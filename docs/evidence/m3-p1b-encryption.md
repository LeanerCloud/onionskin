## The handler, and where its known answers come from

ISO 32000 publishes the algorithms and no test vectors. So the known answers
come from **qpdf**: `corpus/make-encrypted.py` writes one fixture per revision
through pikepdf - `/R` 2 RC4-40, `/R` 3 RC4-128, `/R` 4 with RC4 and with AES-128
crypt filters, `/EncryptMetadata false`, object streams, `/R` 6 AES-256 - each
carrying the same plaintext in a content stream (decrypted under `/StmF`) and an
information-dictionary string (under `/StrF`), plus an `/R` 6 file with a user
password. The fixtures are committed: AES needs a random IV, so they cannot be
regenerated byte for byte, and a suite proving the encrypted-source rule must
not be able to pass over an empty directory.

**All eight matched qpdf on the first run**, and so did the four encrypted
files in the fetched veraPDF corpus.

The review risks, each answered by a fixture:

| Risk | How it is caught |
| --- | --- |
| `/R` 6 validated with `/R` 5's single SHA-256 | Mutation: `r6-aes-256.pdf` refuses to open |
| `/EncryptMetadata false` not honoured | `plaintext_metadata_is_left_alone`, two fixtures |
| Strings inside an object stream decrypted twice | `a_string_inside_an_object_stream_is_decrypted_once_not_twice`, which first asserts the `/Info` really is in an object stream |
| An empty password opening a protected file | `a_document_with_a_user_password_is_refused` |
| Streams and strings keyed alike | Separate tests for each, over every revision |

## The mutation the plan names

Returning the file key unmodified as every object key must fail RC4 and AES-128
while still passing AES-256. `every_revision_decrypts_its_content_stream`
collects failures by fixture rather than stopping at the first, so the output
shows both halves:

```
r2-rc4-40.pdf: the content stream does not decrypt
r3-rc4-128.pdf: the content stream does not decrypt
r4-rc4-128.pdf: the content stream does not decrypt
r4-aes-128.pdf: the content stream does not decrypt
r4-aes-128-plain-metadata.pdf: the content stream does not decrypt
r4-aes-128-objstm.pdf: the content stream does not decrypt
```

`r6-aes-256.pdf` is absent: it passes, because AES-256 uses the file key
directly. That is why the fixtures cover every revision - a suite with only an
AES-256 fixture passes this mutation.

The second mutation - making the encrypted-source predicate always answer
"available" - fails the three `core::protection` tests that drive it.

## Two refusals, one predicate, derived not flagged

`core::protection::read_out` is **the one predicate**: whether a document's
object graph may be read out into any other document. `edit` is the same
answer, asserted equal to it over every encrypted fixture and two plain seeds.

- **Editing** is refused inside `EditSession::transact`, before the body runs -
  the one door every tool, command and verb goes through. Nothing can begin an
  edit on an encrypted document by any route, and nothing is half-written.
- **The shell reports it** through the same query. `Requirement` moved out of
  the context menu into `plugin-api` (P7's deferred work, unblocked now the
  shell builds here) and takes a `Session` carrying the document's refusal. An
  entry whose tool edits - classified once, by `ToolCapability::edits_document`
  - is disabled with the document's own reason. The quick-action toolbar gets a
  `Refused` state for the same reason: the tool has been delivered, and it is
  the document that refuses. Both are asserted to gate **exactly** the editing
  entries and leave the rest untouched.
- **The open-time notice** is a `CanvasStatus::Notice` set when the canvas is
  built, so it is on screen from the first frame. It says what the user can and
  cannot do in words, and states ruling A's residual when `/P` bit 4 is set:
  other editors may let the user change this document now.

An encrypted document still previews: its preview is the file itself, because
an empty overlay has no section. That ordering - `Ok(None)` for an empty
overlay on a clean document, `Err(EncryptedWrite)` only when bytes would be
emitted - was already in `cos`, and is now asserted from both sides.

## `Requirement::Command` turns the milestone guesses into queries

The context menu's four entries that named "M3" as a guess are registry queries
now: Copy With Formatting, Export Selection As, Add Bookmark, Print and Page
Commands each go live when a plugin registers the command id they ask for. The
ids are constants in `plugin-api::command_ids`, so the package that lands each
command registers exactly that constant - a misspelling is a compile error, not
an entry that never goes live. `no_milestone_reason_names_m3` asserts none is
left; `print_and_add_bookmark_go_live_when_their_command_is_registered` asserts
the query works in both directions.

`docs/evidence/encryption-classes.md`, generated by an asserted test. Four
encrypted files in the fetched corpus, all four opened by the empty user
password, **one** with `/P` bit 4 set - the residual ruling A accepted, measured

## Not done here

- **The registry-exhaustive sweep of the encrypted-source rule** is P20's, as
  the plan says: this package's app build registers no plugin that reaches
  `write_new`, so there is nothing to sweep yet. Each later package that adds
  such a command asserts its own refusal through `read_out`.
- **Print-to-file with Print as Image** is P15's to wire; `read_out` is the
  predicate it will call.
- **No `/P` bit is enforced.** Editing is off on every encrypted document, which
  is stricter than any bit, and nothing else is gated by them; a document whose
  `/P` forbids printing can still be printed as a raster. Permission
  enforcement belongs with the write path at M6. Recorded for the
  `known-issues.md` entry the orchestrator lands from the measurement.
- **Owner-password escalation** is not offered: M3 opens with the user password
  only. The owner check exists for the measurement table and nothing else.
